# 01 — Project Constitution

## Non-Negotiable Principles

1. **Functionality before appearance** — working software is the first success criterion.
2. **Legitimate cost minimization** — optimize for the lowest practical cost, not reckless zero-cost behavior.
3. **Cost is first-class** — every execution is evaluated economically, including nominally free resources.
4. **Verification over assertion** — generated code must be tested; an agent saying “it works” is not evidence.
5. **Persistent continuity** — an agent failure must not erase project knowledge or progress.
6. **Provider independence** — no single model/provider should become architecturally indispensable.
7. **Meta-Agent over model loyalty** — the orchestrator selects resources based on task requirements and current conditions.
8. **Measure before optimizing** — performance, quality, reliability, tokens, latency, and cost are recorded before optimization claims are made.
9. **Free-first, not free-only** — paid resources are acceptable when their incremental value justifies their cost.
10. **Terms-respecting resource use** — never circumvent rate limits, payment controls, identity restrictions, trial restrictions, or provider terms.
11. **Controlled autonomy** — human approval remains in the loop for consequential actions until reliability is demonstrated.
12. **Reproducibility** — experiments, decisions, configurations, and results are versioned.
13. **User choice** — CAOS must support both autonomous build and detailed DIY guidance.

## Engineering Doctrine

**Understand → Research → Decompose → Plan → Select → Execute → Persist → Verify → Recover/Replan → Measure → Deliver.**

## Economic Doctrine

For each task, CAOS should compare practical alternatives across:

- Free/open-source resources
- Published free tiers
- Legitimate trials and discounts
- Low-cost APIs
- Higher-cost services when justified
- Local execution where practical

The optimizer should consider total cost, expected quality, reliability, latency, implementation effort, and opportunity cost—not price alone.

## Research Doctrine

The project must distinguish between:

- capability claims,
- measured performance,
- economic cost,
- reliability,
- resource availability,
- and hypotheses about future performance.

No provider should be considered “best” without task-specific evidence.

## Product Doctrine

CAOS should never force the user into autonomous execution. The user should be able to choose:

1. **Let CAOS build it**, or
2. **Show me how to build it myself.**
